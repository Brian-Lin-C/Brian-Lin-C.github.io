计算机网络（三）网络基础概念

在理解了网络分层和数据封装之后，我们需要掌握衡量网络性能的核心指标，以及网络通信的基本方式。这些概念是网络调优、故障排查和架构设计的基础。

一、网络性能指标

1.1 带宽（Bandwidth）

定义：带宽是指单位时间内能够传输的数据量，通常以比特每秒（bps）为单位。

带宽的类型：

类型 说明 示例
理论带宽 物理介质的最大传输能力 千兆网卡的理论带宽是 1 Gbps
可用带宽 实际可用于数据传输的带宽 扣除协议开销后的实际带宽
瓶颈带宽 端到端路径中最小的链路带宽 决定了整个路径的最大传输速率

提醒自己：

  • 带宽是链路的固有属性，就像水管的直径
  • 带宽不随流量变化而变化（除非动态调整）
  • 带宽 ≠ 速度，带宽大不代表延迟低

1.2 吞吐量（Throughput）

定义：吞吐量是指单位时间内实际成功传输的数据量。

影响吞吐量的因素：

因素 说明
网络拥塞 路由器缓冲区满，丢包重传
协议开销 TCP/IP 头部、确认报文等不携带用户数据
窗口大小 TCP 窗口太小会限制发送速率
丢包率 丢包导致重传，降低有效吞吐量
应用层效率 应用层协议设计不合理

提醒自己：

  • 带宽是”能力”，吞吐量是”实绩”
  • 测试网络质量时，吞吐量比带宽更有意义
  • iperf3 是测试吞吐量的常用工具

1.3 延迟（Latency）

定义：延迟是指数据从发送端到接收端所需的时间，也称为时延。

延迟的组成

各种介质的传播速度：

介质 传播速度 每 1000 km 的传播时延
真空 300,000 km/s 3.33 ms
光纤 200,000 km/s 5 ms
铜缆 200,000 km/s 5 ms
同轴电缆 200,000 km/s 5 ms

提醒自己：

  • 发送时延看带宽，传播时延看距离
  • 局域网内传播时延可以忽略，广域网不可忽视
  • 卫星通信的传播时延很大（约 270 ms）

1.4 RTT（往返时间）

定义：RTT（Round-Trip Time）是指从发送方发送数据开始，到发送方收到接收方的确认所经历的时间。

RTT 的重要性：

场景 说明
TCP 重传 RTO（重传超时时间）基于 RTT 计算
拥塞控制 RTT 增加通常意味着网络拥塞
性能优化 减少 RTT 比增加带宽更重要（对交互式应用）

不同距离的 RTT 参考值：

距离 典型 RTT 场景
同一机房 < 0.1 ms 内网通信
同城 1-3 ms 同城多活架构
跨省 20-50 ms 国内访问
跨国（亚洲） 50-100 ms 访问亚洲其他国家
中美之间 130-200 ms 跨太平洋访问
卫星链路 500+ ms 卫星互联网

提醒自己：

  • RTT 受物理距离限制，无法通过技术手段无限降低
  • 光速是硬限制：1 ms 的传播时延对应约 200 km 的光纤距离
  • 优化网络性能时，减少请求次数比减少数据量更重要

二、通信方式

2.1 单工、半双工、全双工

定义：描述数据传输的方向性。

实际应用对比：

方式 例子 说明
单工 光纤到户（GPON）下行 用户只能接收，不能发送
半双工 传统 WiFi（802.11） 同一时刻只能收或发
全双工 有线以太网（1000BASE-T） 同时收发，效率最高

提醒自己：

  • 全双工需要独立的收发信道（如两根光纤或四对双绞线）
  • 半双工需要冲突检测机制（CSMA/CD）
  • 现代网络基本都是全双工

2.2 单播、广播、组播、任播

定义：描述数据包的目标地址类型。

单播（Unicast）

广播（Broadcast）

组播（Multicast）

组播地址范围：

范围 地址段 用途
本地链路组播 224.0.0.0/24 网络协议使用（如 OSPF、RIP）
全局组播 224.0.1.0-238.255.255.255 应用层组播
管理范围组播 239.0.0.0/8 组织内部使用

任播（Anycast）

四种通信方式对比：

类型 目标 例子 效率
单播 一个特定主机 HTTP、SSH 高（精确送达）
广播 广播域内所有主机 ARP、DHCP 低（全部接收）
组播 组内所有主机 视频会议、直播 高（只发给需要的人）
任播 最近的一个主机 DNS、CDN 高（自动优化）

提醒自己：

  • 单播是日常开发最常用的
  • 广播要小心使用，避免广播风暴
  • 组播适合实时流媒体，但需要网络设备支持
  • 任播是大型互联网服务的标配（如 8.8.8.8）

优化手段 效果 适用场景

使用 UDP 无连接开销 实时音视频

4.3 面试常见问题

Q1：为什么 100M 宽带的下载速度只有 10MB/s？

答：运营商说的 100M 是指 100 Mbps（兆比特每秒），而下载软件显示的是 MB/s（兆字节每秒）。1 字节 = 8 比特，所以理论最大速度是 100 ÷ 8 = 12.5 MB/s。扣除协议开销（TCP/IP 头部、确认报文等）后，实际约 10-12 MB/s 是正常的。

Q2：为什么游戏对延迟敏感，而视频播放对带宽敏感？

答：游戏是交互式应用，玩家操作需要立即反馈，延迟超过 100ms 就会感觉卡顿。视频播放可以预缓冲，只要带宽足够下载速度大于播放速度，就不会卡顿，延迟 200ms 也无感知。

Q3：TCP 窗口大小对性能有什么影响？

答：TCP 窗口决定了发送方在收到确认前可以发送多少数据。如果窗口太小，发送方会频繁停下来等待确认，无法充分利用带宽。特别是在高延迟网络中，窗口需要足够大才能”填满”RTT 时间内的链路。

Q4：什么是”长肥管道”问题？

答：长肥管道（Long Fat Pipe）指高带宽 × 高延迟的网络（如卫星链路）。这种网络需要非常大的 TCP 窗口才能充分利用带宽，对传统 TCP 是个挑战。
